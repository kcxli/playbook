# Private Applicant Profile Questions

This document is the intake blueprint for real applicants. Shared facts used by
any maintained playbook belong here and are collected once. A target answer set
is reserved for referral, institution relationships, or a genuinely unique
prompt that cannot be derived safely.

The goal is not to ask every possible application question up front. The goal is
to collect enough structured data that most playbooks can run without inventing
answers or asking the applicant the same basic question repeatedly.

For the full architecture tying this intake model to playbooks, generated
`app_answers`, employer exceptions, equivalence matching, and the Project
Exchange flow, see [application-answer-system.md](application-answer-system.md).

The implemented machine-readable version of this blueprint is
`playbook_runner/intake.py`. Update that contract and its tests when a maintained
playbook introduces a new required profile or position-specific field.

## Rules For Consistent Answers

- Use the canonical values below in applicant JSON. The runner can translate
  common display variants such as `TX`/`Texas`, `U.S.A.`/`United States`, and
  `Ph.D.`/`Doctorate`, but the profile itself should stay consistent.
- Use `true`/`false` for yes/no facts whenever possible.
- Use `YYYY-MM-DD` for full dates, `YYYY-MM` when only month/year is known, and
  a four-digit year when a form only asks for year.
- Use `""` for optional text that the applicant did not provide.
- Use `null` only when the value is truly unknown or intentionally not collected.
- Do not store secrets in the basic profile. Account passwords, email app
  passwords, and API keys belong in gitignored secret files or environment vars.
- Do not coerce an applicant into a demographic answer. For constrained forms,
  the safe canonical value is usually a decline option, not a guessed category.

## How Playbooks Should Use These Answers

Playbooks should use three layers:

| Layer | Use it for | Example |
|---|---|---|
| Canonical profile paths | Stable applicant facts with a natural home | `person_name.legal_name.first`, `education.schools.0.institution`, `documents.resume_path_or_url` |
| Generated application answers | Reusable answers to common application questions | `app_answers.referral_source`, `app_answers.authorized_to_work_us`, `app_answers.desired_salary` |
| Position overrides | Facts that can change for one listed position | `position_overrides.referral_source`, `position_overrides.employment_relationship` |
| Protected runtime `answers.*` | Sensitive checkpoint values that are never ordinary JSON | `answers.cuhk_id_number`, `answers.ua_felony_conviction` |

`app_answers` is generated by the runner. Do not ask applicants to fill it in
directly. It is built from canonical profile facts, global defaults, legacy
employer exceptions, and the current target's nonblank position overrides.

Use these default/exception buckets in applicant JSON when a question is common
but not a fixed biographical fact. In the intake UI, ask this as "What should we
answer by default?" plus an optional "Add employer exception" control keyed by
the playbook's `employer_key`.

```json
{
  "application_defaults": {
    "authorized_to_work_us": true,
    "requires_visa_sponsorship": false,
    "referral_source": "Job Board",
    "specific_referral_source": "",
    "previously_employed_by_employer": false,
    "related_to_employer_employee": false,
    "has_conflict_of_interest": false,
    "desired_salary": "82000"
  },
  "application_exceptions": {
    "umn": {
      "referral_source": "HERC",
      "specific_referral_source": "HERC statistics faculty mailing list"
    }
  }
}
```

This means the applicant can say "use Job Board by default" once, and only
record exceptions for employers where that answer should differ. Playbooks then
read `app_answers.referral_source` and do not need to know where the value came
from.

### General Application Defaults

Ask these once in the basic profile because they appear across many
applications. They should not create a new per-application prompt unless the
applicant adds an exception.

| Default question | JSON path | Permitted response |
|---|---|---|
| Are you currently authorized to work in the United States? | `application_defaults.authorized_to_work_us` | `true` / `false`; leave `null` only while the profile is incomplete |
| Will you now or in the future require visa sponsorship? | `application_defaults.requires_visa_sponsorship` | `true` / `false`; should match `detailed_personal_info.birth_and_citizenship.requires_visa_sponsorship` |
| Desired salary to use when a form requires a number or range | `application_defaults.desired_salary` and `employment_basics.salary_expectation.amount_target` | Plain number string such as `"82000"`, or `""`; dropdown ranges are matched deterministically |
| Salary period | `application_defaults.salary_period` | `annual`, `hourly`, `monthly`, `weekly` |
| Default referral/source answer | `application_defaults.referral_source` | `Employer Website`, `Job Board`, `LinkedIn`, `Indeed`, `HigherEdJobs`, `HERC`, `Chronicle`, `Professional Organization`, `Employee Referral`, `Recruiter`, `Social Media`, `Other` |
| Default referral/source detail | `application_defaults.specific_referral_source` | Text or `""` |
| Default employee referral answer | `application_defaults.employee_referral` | `true` / `false` |
| Default employee referrer name | `application_defaults.employee_referrer_name` | Text or `""` |
| Default employee referrer relationship | `application_defaults.employee_referrer_relationship` | Text or `""` |
| Have you previously worked for the employer? | `application_defaults.previously_employed_by_employer` | `true` / `false` |
| Previous employer details | `application_defaults.previously_employed_by_employer_details` | Text or `""` |
| Previous employee ID | `application_defaults.previous_employer_employee_id` | Text or `""` |
| Are you related to an employee of the employer? | `application_defaults.related_to_employer_employee` | `true` / `false` |
| Related employee details | `application_defaults.related_to_employer_employee_details` | Text or `""` |
| Conflict of interest disclosure | `application_defaults.has_conflict_of_interest` | `true` / `false` |
| Conflict of interest details | `application_defaults.has_conflict_of_interest_details` | Text or `""` |
| Claim veteran's preference in hiring, when offered | `application_defaults.claims_veterans_preference` | `true` / `false`; employer exceptions may override |
| Has a government agency excluded you from receiving government funds or participating in a government program? | `application_defaults.excluded_from_government_program` | `true` / `false`; ask carefully because this is a legal/compliance question |
| Government-program exclusion details | `application_defaults.excluded_from_government_program_details` | Details if `true`; usually `N/A` if `false` |

Employer exceptions go under `application_exceptions.<employer_key>` using the
same keys. Example: if the default is "not previously employed" but the
applicant had a temporary NYU Langone appointment, set
`application_exceptions.nyulangone.previously_employed_by_employer` to `true`
and put the details beside it.

Do not put felony/conviction, SSN, government ID, banking, or payment questions
in these defaults. Those are legally or financially sensitive and should be
handled only when a specific playbook requires them.

Do not ask applicants to invent account usernames, passwords, or plus-tagged
emails in the intake form. Playbooks should use `generated_values` for those
run-specific values and the runner records them locally in `.run/`.

## Core Questions To Ask Everyone

### 1. Name

Required:

| Question | JSON path | Permitted response |
|---|---|---|
| Legal first name | `person_name.legal_name.first` | Text |
| Legal middle name | `person_name.legal_name.middle` | Text or `""` |
| Legal last name | `person_name.legal_name.last` | Text |
| Suffix | `person_name.legal_name.suffix` | `""`, `Jr.`, `Sr.`, `II`, `III`, `IV`, or site-specific text |
| Preferred first name | `person_name.preferred_name.preferred_first` | Text or `""` |

Optional:

| Question | JSON path | Permitted response |
|---|---|---|

| Prior legal names | `person_name.prior_legal_names` | List of `{ full_name, from_date, to_date, reason }`; ask only if a form requires it |

### 3. Work Authorization

These are common screening questions. Ask them once because many applications
block progress without them.

| Question | JSON path | Permitted response |
|---|---|---|
| Are you currently authorized to work in the United States? | `application_defaults.authorized_to_work_us` or legacy `answers.authorized_to_work_us` | `true` / `false`; playbooks read `app_answers.authorized_to_work_us` |
| Will you now or in the future require visa sponsorship? | `detailed_personal_info.birth_and_citizenship.requires_visa_sponsorship` | `true` / `false` |
| Citizenship country | `detailed_personal_info.birth_and_citizenship.citizenship_country` | Country name or `""` |
| Current visa/work status, if relevant | `detailed_personal_info.birth_and_citizenship.visa_status.type` | `""`, `US Citizen`, `Permanent Resident`, `Noncitizen National`, `Alien Authorized to Work`, `F-1 OPT`, `STEM OPT`, `H-1B`, `TN`, `J-1`, `Other` |
| Visa/status expiration date, if relevant | `detailed_personal_info.birth_and_citizenship.visa_status.expiration_date` | `YYYY-MM-DD` or `""` |

Do not ask for SSN, passport numbers, government ID numbers, bank details, or
payment information in the basic profile.

### 4. Education

only when an application requires full education history.

| Question | JSON path | Permitted response |
|---|---|---|
| Highest education level | `education.highest_level` | `High School`, `Associate`, `Bachelors`, `Masters`, `Doctorate`, `Professional Degree`, `Other` |
| School / institution | `education.schools.0.institution` | Text |
| Degree | `education.schools.0.degree` | `High School`, `Associate`, `Bachelor of Arts`, `Bachelor of Science`, `Master of Arts`, `Master of Science`, `MBA`, `Ph.D.`, `Ed.D.`, `J.D.`, `M.D.`, `Other` |
| Major / field of study | `education.schools.0.major` | Text |
| Minor | `education.schools.0.minor` | Text or `""` |
| School city | `education.schools.0.city` | Text or `""` |
| School state/province | `education.schools.0.state_province` | Text or `""` |
| School country | `education.schools.0.country` | Country name |
| Start date | `education.schools.0.start_date` | `YYYY-MM`, `YYYY-MM-DD`, year, or `""` |
| Graduation month | `education.schools.0.graduation_date` | `YYYY-MM` or `""` |

Academic facts such as discipline, publication details, research interests,

## Voluntary Demographics

These should be clearly labeled as voluntary. The applicant must be able to skip
or decline. Store the automation-facing answer in the canonical values below.

### Gender

| Question | JSON path | Permitted response |
|---|---|---|
| Gender for application forms | `answers.gender` | `Male`, `Female`, `I do not wish to provide this information` |
| Identity/pronouns for applicant record | `identity_and_status.gender.value`, `identity_and_status.pronouns.set` | Optional text; not used to force form answers unless the site supports it |

Many forms only support `Male`/`Female` plus a decline option. Do not map a
non-binary identity to `Male` or `Female`. If a site does not support the
applicant's identity, use the decline value unless the applicant explicitly
chooses one of the available form options.

### Hispanic / Latino

| Question | JSON path | Permitted response |
|---|---|---|
| Do you identify as Hispanic or Latino? | `answers.is_hispanic_or_latino` | `Yes`, `No`, `I do not wish to provide this information` |

## Position-Specific Add-On Questions

Do not put every one-off field into the basic intake. First ask whether the
field is really just a common application answer. If yes, store it in
`application_defaults` or `application_exceptions.<employer_key>` and have the
playbook read `app_answers.*`.

When a playbook needs a true target value, add it under
`position_overrides.*`. Current examples are CUHK's role selection and NYU's
license option. Government IDs and criminal-history responses stay under the
protected runtime `answers.*` namespace and never enter `ApplicationAnswerSet`.

Good site-specific questions are:

- Required by the playbook.
- Hard to infer safely.
- Stable enough to reuse across applications on the same platform.
- Not already covered by canonical profile facts, equivalences, or
  `app_answers`.

Poor site-specific questions are:

- Sensitive information that should not be stored.
- Free-form answers that should be tailored per job.
- Final attestation/submission choices that require human review.

## Minimum Basic Profile Checklist

For the first usable intake form, collect only these:

1. Legal name.
2. Primary email and mobile phone.
3. Primary address.
4. Work authorization and sponsorship.
5. Highest/primary education.
6. Current or most recent job.
7. Resume/CV file.
8. Optional cover letter and common academic documents.
9. One reference, with the option to add more.
10. Voluntary demographics, each with a decline option.
11. General application defaults: referral source, prior employer, related
    employee, and conflict-of-interest defaults, with optional employer
    exceptions.
12. Start date, salary expectation, relocation/travel preferences.

Everything else should appear only when the applicant selects a job family or
when a specific playbook says it is required.
